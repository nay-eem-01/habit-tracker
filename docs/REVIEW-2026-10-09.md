# DevHabit — Product and Code Review (2026-10-09)

What this covers: (A) is the product something people would use and pay for, (B) what blocks a
real launch, security included, (C) bugs found while reading, (D) a "ponytail" pass for
over-engineering, (E) heavy-looking parts that are worth keeping, (F) a suggested order.

This is a read-only review. **Nothing in the code was changed.** I read `src/main` (124 files,
about 6,000 lines), the config, `logback-spring.xml`, the migrations list, `docs/ROADMAP.md` and
the frontend's folder layout (`habit-tracker-web/src`). I did not run the app or the tests (the
repo has 268 `@Test` methods in 54 files).

Each finding has a number so you can say "do B3, skip D5".

---

## Verdict in one paragraph

The engineering is well above average for a solo project: ownership checks everywhere, hashed
rotating refresh tokens, numbers computed from logs instead of stored, timezone-correct "today",
upserts that survive races, and real integration tests on PostgreSQL. **As a product, it is not
yet something people would pay for.** Today it is a competent web-only habit tracker, and that
market is crowded with mature, mostly mobile apps, several of them free. What it lacks is not
polish but a reason to choose it: phone-first daily use (push notifications, home-screen
install), forgiving streaks, and a clear audience. The name "DevHabit" and the goals + resources
features already point at a niche worth committing to: **self-directed learners and developers
tracking learning goals.** Commit to that niche, add automatic check-ins from tools developers
already use (A6), and a paid tier starts to make sense.

## Part A — Product review

### A1. The core problem: a crowded market and no stated reason to switch
Habit trackers are one of the most crowded app categories (Habitica, Streaks, Habitify, Loop Habit
Tracker, which is free and open source, TickTick's habits, Productive, Atoms, and others).
Users switch for one of three things: (1) a better daily experience on their phone, (2) a feature
nobody else has, or (3) a community. DevHabit has none of these yet. Daily, strict, timezone-aware
streaks with 7/30/90-day stats are table stakes: every competitor has them.
**Action:** write one sentence for "who it is for and why not Habitify", and decide features by it.
My suggestion is in A6.

### A2. Web-only is the biggest adoption risk
Checking in is a 2-second action done many times a day, usually on a phone. A web SPA behind a
login, with no home-screen install, no offline check-in and no push, loses that habit loop to
any native app. The frontend has no `manifest`, no service worker, no push.
**Action (cheapest path):** make the web app a **PWA** (installable, offline-tolerant check-in
queue, Web Push for reminders). That is far cheaper than native apps and covers Android and,
since iOS 16.4, home-screen web apps on iPhone. Native apps can come later, if ever.

### A3. Reminders by email will hurt more than help
Today a reminder is an in-app notification plus, when email is on, **one email per habit per
day for every user** (`ReminderService.sendDue` → `OutgoingNotification` → SMTP). Five habits
means five emails a day. People will unsubscribe, mark it as spam, and your sending domain's
reputation then also hurts password-reset emails. There is also **no per-user setting** to turn
reminder emails off; `app.notifications.email.enabled` switches it for everyone.
**Action:** reminders go to Web Push (A2). Email is used for account email (reset, verify) and at
most **one daily or weekly digest**, with a per-user opt-out and an unsubscribe link (see B6).

### A4. Strict streaks with no forgiveness push people to quit
`StreakCalculator` is strict: one missed scheduled day resets the run. Duolingo-style apps
learned that a broken streak is the moment users churn. Missing:
- **Skip / rest day** (a day marked "skipped" neither breaks nor extends the streak).
- **Streak freeze** (earned with XP — this also gives XP a use, which it has none of today).
- **Pause / vacation mode** for a habit or the whole account (dates during which nothing is due).
These fit the existing design: `StreakCalculator.walk` already skips days that are not scheduled,
so a "not scheduled because paused or skipped" day is a small extension.

### A5. Missing basics users will expect on day one
1. **Edit profile: name and especially timezone.** There is no endpoint to change `User.timezone`.
   Someone who travels, or who registered with the default `UTC`, gets the wrong "today" for
   check-ins, reminders and streaks, with no way to fix it.
2. **Delete my account** and **export my data (CSV/JSON)**. Required by GDPR for EU users, and
   Apple and Google require in-app account deletion if you ever ship to their stores.
3. **Email verification** at sign-up (also a security issue, see B2).
4. **Units on counted habits.** `targetCount = 8` means "8 of what?" A unit label ("glasses",
   "pages", "minutes") is one column.
5. **Habit order.** Users want to arrange the Today list themselves; it is sorted by name today.
6. **"Quit" habits** (don't smoke, no sugar): shown as "days since last slip". This is a large
   share of what people track, and it doesn't fit the "check in to do" model yet.
7. **Hard delete of a habit** (archive is good, but people also want to remove a mistake).

### A6. The differentiator I'd bet on: "habits that check themselves" for learners and developers
The name and the M2/M3 features (goals with target days, notes, links, files next to a goal)
already describe a **learning tracker**: "Learn Rust in 60 days", with habits that feed the goal
and the material in one place. Commit to that and add what generic trackers can't do well:
- **Automatic check-ins from integrations**: GitHub (committed today), LeetCode / Codewars
  (solved a problem), WakaTime (coded ≥ N minutes), Anki (did reviews), Duolingo, Strava,
  Apple Health / Google Fit later. Auto check-in removes the most tedious part of habit apps,
  and it is something people pay for.
- **Learning goals as first-class**: a goal with a syllabus (ordered resources), progress from
  both habits and finished resources, and a "what to do today" suggestion.
- **Public profile / shareable streak card** (like a GitHub contribution graph). This is free
  marketing, and developers like showing these off.
- **Accountability partner**: share one goal with a friend who sees your check-ins. Social
  accountability is one of the strongest retention levers in this category.
- **Weekly review email/page**: what went well, weakest weekday, streaks at risk. The data is
  already computed (`PatternCalculator`, `HighlightCalculator`); this mostly needs presentation.

### A7. What a paid tier could contain (and what must stay free)
Free must be a complete, good habit tracker: otherwise people never get as far as paying.
A plausible split:
- **Free:** up to ~5–7 active habits, reminders, streaks, 30-day stats, notes and links.
- **Pro (monthly or yearly):** unlimited habits, integrations / auto check-ins (A6), full history
  and patterns (heatmap, time-of-day), streak freezes, file attachments, data export as
  CSV, AI weekly insights (M6), themes. Consumer habit apps typically charge a few dollars a
  month; check current competitor pricing before you set yours.
- Technically: a `plan` on `User`, a single `Entitlements` check where limits are enforced, and a
  hosted checkout (Stripe, Paddle or Lemon Squeezy — the last two handle sales tax for you) with
  a webhook. Don't build billing until there are users who would pay.

### A8. Features I'd question before investing more
- **File uploads (R.3, R.3d S3).** For a habit tracker, files are a low-value feature with real
  cost: storage bills, a malware/abuse surface, quota and orphan handling, and an S3 step that is
  now on your blocker list. Notes and links cover most needs. **Recommendation: launch without
  file uploads** (hide the endpoint/UI), or keep local disk on a single server and do S3 only if
  Pro users ask for files. That removes a launch blocker.
- **AI insights (M6).** Everyone is adding this; on its own it won't sell the product. Do it after
  A2–A6, as a Pro feature that is built on the weekly review.
- **Levels and tiers (M4).** Cheap and fun, keep them, but XP has no use. Spending XP on streak
  freezes (A4) gives it a purpose.

### A9. Validate before building much more
Before Phase "make it great", put the current version in front of **10–20 real people** in the
target niche for 2–3 weeks. Watch who still checks in on day 14. Add basic product analytics
(sign-up → first habit → first check-in → day-7 retention), privacy-friendly (Plausible, PostHog
self-hosted, or a simple events table). Without this you are guessing which of A2–A7 matter.

## Part B — Launch blockers and security

### B1. Google sign-in (2.3): use the ID-token flow, and drop the unused OAuth2 client
The plan (ID token from Google Identity Services, verified on the server) is right for an SPA. To
build it:
- Verify the token with Google's public keys: `NimbusJwtDecoder.withJwkSetUri("https://www.googleapis.com/oauth2/v3/certs")`
  from `spring-security-oauth2-jose`, then check `iss` is `accounts.google.com` or
  `https://accounts.google.com`, `aud` equals **your** client id, `exp`, and `email_verified == true`.
  Look users up by Google's `sub` (`providerId`) first, email second.
- `spring-boot-starter-security-oauth2-client` (and its `-test` starter) is in `pom.xml` but
  nothing in `src/main` uses it, and the redirect flow it implements is not the one you chose.
  Remove it; add only the JOSE module above.

### B2. Account pre-hijacking risk when Google linking arrives (must fix with 2.3)
Sign-up does not verify email ownership. Scenario: an attacker registers `victim@gmail.com` with a
password they know. Weeks later the real owner clicks "Sign in with Google"; the planned
"find, create or **link by verified email**" links Google to the attacker's account. Now both can
sign in, and the attacker reads everything the victim writes.
**Fix (pick one):** (a) add email verification at sign-up and only link to verified accounts;
or (b) when Google links to an unverified LOCAL account, remove its password, revoke all its
refresh tokens and reset links, and mark it verified. (a) is cleaner and also fixes A5.3.

### B3. No rate limiting on login, register, refresh or forgot-password
`POST /api/auth/login` can be brute-forced at full speed; `register` can be scripted to create
accounts; `forgot` is limited per account (good) but not per IP or overall, so one script can
email thousands of different addresses through your domain and damage its sending reputation.
**Fix (smallest):** rate-limit at the reverse proxy or CDN (nginx `limit_req`, Cloudflare rules)
on `/api/auth/*`, plus a per-account failed-login counter with a short lockout. Use Bucket4j in the
app only if there is no proxy.

### B4. Passwords longer than 72 bytes probably cause a 500 (verify with a test)
`RegisterRequest` / `ChangePasswordRequest` allow up to 100 characters, but BCrypt only handles
72 **bytes**. Recent Spring Security versions make `BCryptPasswordEncoder` throw
`IllegalArgumentException` above 72 bytes instead of silently truncating — that would surface as
a 500. Non-ASCII passwords reach 72 bytes with fewer characters.
**Check:** a test that registers with an 80-character password. **Fix:** cap at 72 bytes in
validation (a custom check, since `@Size` counts characters), or move to Argon2 via
`DelegatingPasswordEncoder`.

### B5. Production profile (D.2) is still open, and the defaults are dev settings
`application.properties` currently has `show-sql=true`, `logging.level.org.springframework.security=DEBUG`,
`com.nayeem.habittracker=DEBUG`, `org.apache.http=DEBUG`, Swagger on, and CORS defaulting to
`http://localhost:3000` (the frontend runs on 5173). Security DEBUG logs request details for every
request. **Fix:** D.2 as planned — an `application-prod.properties` with INFO, no SQL, Swagger off,
`CORS_ALLOWED_ORIGINS` required (no default).

### B6. Real email sending: provider, DNS and the mail itself
- Use a transactional provider (Postmark, Resend, Amazon SES, Brevo) rather than Gmail SMTP —
  Gmail app passwords have low daily limits and poor deliverability from servers.
- Set **SPF, DKIM and DMARC** on the sending domain, or reset emails will land in spam.
- Separate **transactional** mail (reset, verify) from **notification** mail (reminders, digest);
  many providers use separate streams so complaints about reminders don't hurt resets.
- Notification mail needs a per-user opt-out and a `List-Unsubscribe` header (Gmail and Yahoo
  require one-click unsubscribe for bulk senders).
- Plain-text email is fine to launch with; HTML templates can wait.
- Today, sending happens synchronously in the `AFTER_COMMIT` listener on the request thread (for
  resets) or the scheduler thread (for reminders). A slow SMTP server slows `forgot-password`
  responses, and with many reminders a single minute's run can take longer than a minute. Making
  the listener `@Async` is the one-line fix.

### B7. The refresh cookie only works if the frontend and API are on the same site
The refresh cookie is `SameSite=Strict`, path `/api/auth`. If the SPA is on `app.vercel.app` and
the API on `api.onrender.com`, those are **different sites**: the browser will never send the
cookie, and every user is logged out after 15 minutes. **Decide the topology before deploying:**
serve the API under the same domain (`devhabit.com/api` through a proxy) or on a subdomain of the
same registrable domain (`app.devhabit.com` + `api.devhabit.com`).

### B8. Deployment basics that don't exist yet
- No `Dockerfile`, no CI (`.github/` doesn't exist). Add a CI workflow that runs `./mvnw verify`
  (Testcontainers works on GitHub runners) on every PR to `staging`/`main`.
- Logs: in a container, log to **stdout only**; the rolling file appender (5 GB cap, 30 days)
  writes to an ephemeral disk that disappears on redeploy. Keep the file appender for local runs.
- Database backups (managed Postgres with point-in-time restore) and a tested restore.
- Expired `refresh_tokens` and `password_reset_tokens` are never deleted; a row is added on every
  login and refresh. Add a daily cleanup (`delete … where expires_at < now() - interval '30 days'`).
- Uptime check on `/actuator/health` and error alerting (Sentry free tier, or the log platform).

### B9. Smaller security notes
- `JwtAuthenticationFilter` loads the user from the database on every request (by email). That is
  correct (deleted users lose access at once) and fine at this scale; just know that every API
  call costs one query.
- `FileService.store` checks the quota then writes, without a lock: two uploads at the same moment
  can both pass and exceed the quota a little. Acceptable; note it rather than fix it.
- JWTs have no `iss`/`aud`. Fine while only this API issues and reads them.

## Part C — Bugs and correctness issues found while reading

### C1. Changing a habit's target or schedule rewrites its whole history
Done days are computed with the habit's **current** `targetCount` (`HabitLogRepository.findDoneDays`:
`l.completedCount >= l.habit.targetCount`) and the **current** frequency. Raise "drink water"
from 1 to 8 and every past day with a count of 1 stops being done: the streak resets to 0, stats
drop, goal progress drops, and **XP is taken back** — which breaks the "XP is never lost" rule (Q8).
Switching DAILY → SPECIFIC_DAYS also re-judges the past.
**Fix options:** (smallest) store `done` (or the target at the time) on each `habit_logs` row when
it is written and count that; or treat a target/schedule change as a new "version" starting today.
The first is one column plus a backfill migration.

### C2. One bad habit stops every reminder for that minute
`ReminderService.sendDue` runs all due habits in **one transaction**. If any row fails (an invalid
stored timezone, a constraint error), the whole minute rolls back and no one gets a reminder; the
scheduler logs it and moves on to the next minute, so that minute's reminders are lost. Process
each habit in its own transaction (or catch per habit) so one bad row only affects itself.

### C3. `RefreshTokenService` uses `Instant.now()` while everything else uses the injected `Clock`
`issue` and `consume` call `Instant.now()`; `PasswordResetService` and the rest use `clock`. Tests
can't pin refresh-token time, and it is inconsistent. A two-line change.

### C4. `markAllRead` loads every unread row to update it
`NotificationService.markAllRead` reads all unread notifications into memory and saves them one
by one. A single `update notifications set read_at = :now where user_id = :id and read_at is null`
(returning the count) is simpler and constant-cost.

## Part D — Ponytail pass: what is over-engineered

Overall: the code is **not** badly over-engineered — classes are small, there is no layer cake,
no mapper library, no premature microservices. The weight is mostly in **infrastructure and
config**, not in the domain code. The findings, from most to least worth acting on:

### D1. OpenTelemetry is installed only to print ids that you already have
`opentelemetry-spring-boot-starter` + the alpha BOM + the MDC appender are there so every log line
has `trace_id`/`span_id`, but all three exporters are `none`. `CorrelationIdFilter` already gives
every request an id that is in every log line, in the response header and in error bodies. So
every line now carries **three** ids (`trace`, `span`, `cid`) for the same request, and the app
pays for auto-instrumentation (startup time, an extra dependency tree, an alpha BOM) for nothing it
exports. **Simplest:** remove OTel until there is a collector to send traces to; keep `cid`. If you
want OTel later, use it *instead of* the correlation id, not alongside it.

### D2. Async appenders that can drop logs, for a low-traffic app
`ASYNC_FILE` and `ASYNC_STDOUT` have `neverBlock=true`: when the queue is full, events —
**including ERRORs** — are silently dropped. At this traffic the synchronous appenders cost nothing
measurable, and losing the error line during an incident is the worst time to lose it.
**Simplest:** remove the async wrappers (or at least set `neverBlock=false`). Together with B8
(stdout only in containers), `logback-spring.xml` shrinks to about a third.

### D3. Unused dependencies
- `spring-boot-starter-security-oauth2-client` and `spring-boot-starter-security-oauth2-client-test`
  — unused (B1).
- `com.fasterxml.jackson.core:jackson-databind` declared explicitly — Boot 4 uses Jackson 3
  (`tools.jackson`), and `jjwt-jackson` brings its own Jackson 2. Check whether anything needs this
  line; if not, remove it.

### D4. `AppProperties` has dead fields and a doubled annotation
`backendUrlShort` is never read; `name` is used only for the Swagger title (`spring.application.name`
or `display-name` would do). The class is both `@Component` and `@Configuration` — one is enough
(or `@ConfigurationPropertiesScan`). Remove the dead fields.

### D5. `StoredFile.sha256` — computed and stored, never used
The comment says "to spot corruption or duplicates later". Nothing reads it. It costs a
`DigestInputStream` on every upload and a column. Classic YAGNI; drop it, or leave it if you
actually plan dedup soon. Small either way. (If you take A8 and shelve file uploads, this is moot.)

### D6. `LocalDiskFileStorage` and the S3 implementation: pick one for production
The `FileStorage` interface is justified only because a second implementation is planned. If you
deploy to a single server with a persistent disk, local disk is enough and R.3d isn't needed. If
you deploy to a platform with ephemeral disks, you need S3 and local disk becomes a dev-only
convenience (MinIO in Docker could replace it in dev as well, leaving one implementation).
Decide with B7/B8 and A8 instead of building both by default.

### D7. Dashboard returns more numbers than a screen shows
`DashboardResponse` computes 7/30/90-day windows **and** the previous window **and** the change, per
habit and overall, on every load (and the dashboard reloads after every check-in). Check what the
frontend actually displays; if the 90-day and per-habit "previous/change" values aren't shown, drop
them — less code, a smaller payload, less to keep consistent.

### D8. Process docs are heavier than the code needs (mild)
`PLAN.md` (853 lines) + `DEV_LOG.md` (858 lines) + `ROADMAP.md` + five project skills, for a
6,000-line app. That's your chosen workflow and it clearly helps with continuity, so keep it — but
the dev log mostly repeats commit messages and PR descriptions. Shorter entries (what changed,
decisions, gotchas) would cost less to write and read.

## Part E — Looks heavy, but is worth keeping

So these don't get "simplified" by mistake:
- **Native `insert … on conflict` upserts** (check-ins, reminders): the simplest correct answer to
  races and duplicate reminders across instances.
- **Computing streaks, stats, XP and goal progress on read** instead of storing them: less code and
  no drift. It reads all of a user's logs per dashboard load, which is fine for a long time
  (hundreds of habits × years is still small). Only cache if a profile shows it's slow.
- **`StreakCalculator.walk` shared by streaks and XP**: one rule set instead of two copies.
- **`LogbackMaskingPatternLayout`**: a few regexes per line is cheap insurance against tokens in logs.
- **`FileType` magic-number check + extension match, `nosniff`, `attachment`, UUID storage keys**:
  this is the minimum safe upload handling, not over-engineering.
- **Refresh-token rotation with reuse detection, hashed tokens, timing-safe login**: standard and right.
- **`NotificationSender` interface with console and email**: two real implementations, a third (push) coming.
- **`DueRules`, `FrequencyConfig.normalize`, package-private repositories**: small and pay their way.

## Part F — Suggested order

1. **Decide the product direction** (A1, A6) and the deploy topology (B7). They shape everything below.
2. **Launch blockers:** B5 (prod profile), B3 (rate limits), B4 (72-byte check), C1 (history
   rewrite), C2 (reminder isolation), B6 (email provider + DNS + async send), B8 (Dockerfile, CI,
   stdout logs, token cleanup, backups).
3. **Before inviting users:** A5.1 (edit timezone/name), A5.2 (delete account + export), email
   verification (A5.3 / B2), Google sign-in with the B2 protection (B1).
4. **Decide on files** (A8 / D6): ship without uploads, or local disk on one server; S3 only if needed.
5. **Cleanup PRs (small):** D1, D2, D3, D4, C3, C4.
6. **Soft launch to 10–20 people** with basic analytics (A9).
7. **Then the product work:** PWA + Web Push (A2, A3), skip/freeze/pause (A4), integrations and
   learning goals (A6), then a Pro tier (A7).
